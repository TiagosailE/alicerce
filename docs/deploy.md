# Deploy

The public demo runs on Render's free web service with a Supabase free Postgres (reasoning in [ADR 0002](adr/0002-free-hosting.md)). `render.yaml` describes the service; Render deploys `main` after its CI checks pass.

## First setup

1. Supabase: create a project in `us-east-1` and keep its database password in a password manager. In Connect, copy the Session pooler connection string (port 5432, IPv4) with the password filled in.
2. Render: New, Blueprint, choose this repository. Render reads `render.yaml` and asks for `DATABASE_URL`: paste the Supabase string. `SECRET_KEY_BASE` is generated by Render.
3. The first deploy runs `bin/rails db:prepare` from `bin/docker-entrypoint`, which creates the tables.
4. Uptime monitor (UptimeRobot or similar): HTTP check on `https://<host>/up` every 5 minutes.
5. Check: `curl -sI https://<host>/up` answers 200 and `https://<host>/` answers the SPA with the `content-security-policy` header.

## Environment

| Variable | Source | Purpose |
|---|---|---|
| `DATABASE_URL` | Supabase session pooler | Database, jobs and cache |
| `SECRET_KEY_BASE` | generated by Render | Signed and encrypted cookies |
| `APP_HOST` | optional; defaults to `RENDER_EXTERNAL_HOSTNAME` | Host allow list and links in emails |
| `WEB_CONCURRENCY`, `RAILS_MAX_THREADS`, `SOLID_QUEUE_IN_PUMA`, `JOB_THREADS` | `render.yaml` | One Puma process with jobs inside, under 512 MB |

## Rotating secrets

- Database password: reset it in Supabase (Database settings), update `DATABASE_URL` on Render, and Render redeploys. Open connections from the old password fail until the new deploy is live, a few seconds of errors.
- `SECRET_KEY_BASE`: generate a new value with `bin/rails secret`, set it on Render. Every session and signed token becomes invalid, so every user signs in again. Rotate it after any suspected leak.
- Any key found in a commit: rotate it first, then remove it from history; a pushed secret is public even after the commit is gone.

## Rollback

Render keeps previous deploys: Deploys, choose the last good one, Rollback. Migrations follow the expand and contract rule, so the previous image works with the newer schema.
