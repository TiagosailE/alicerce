# Deploy

The public demo runs on Render's free web service with a Supabase free Postgres (reasoning in [ADR 0002](adr/0002-free-hosting.md)). `render.yaml` describes the service; Render deploys `main` after its CI checks pass.

## First setup

1. Supabase: create a project in `us-east-1`. In the SQL editor, create the two roles the app uses, with passwords from a password manager:

   ```sql
   create role alicerce_owner login password '<owner password>' nobypassrls;
   create role alicerce_app login password '<app password>' nobypassrls;
   grant usage, create on schema public to alicerce_owner;
   grant usage on schema public to alicerce_app;
   alter default privileges for role alicerce_owner in schema public
     grant select, insert, update, delete on tables to alicerce_app;
   alter default privileges for role alicerce_owner in schema public
     grant usage, select on sequences to alicerce_app;
   ```

   `alicerce_owner` runs migrations and owns the tables; `alicerce_app` serves requests and can only read and write rows. Neither bypasses row level security.
2. Supabase, Database settings: enforce SSL and download the CA certificate. It is committed as `config/certs/supabase-ca.crt` (a public certificate, not a secret).
3. Build the two connection strings from the Session pooler string (port 5432, IPv4), one per role, with the user written as `<role>.<project-ref>` and ending in `?sslmode=verify-full&sslrootcert=/rails/config/certs/supabase-ca.crt`.
4. Render: New, Blueprint, choose this repository. Render reads `render.yaml` and asks for `DATABASE_URL` (the `alicerce_app` string) and `MIGRATION_DATABASE_URL` (the `alicerce_owner` string). `SECRET_KEY_BASE` is generated by Render.
5. The first deploy runs `bin/rails db:prepare` as the owner from `bin/docker-entrypoint`, which creates the tables, then starts the server as the app role.
6. Uptime monitor (UptimeRobot or similar): HTTP check on `https://<host>/up` every 5 minutes.
7. Check: `curl -sI https://<host>/up` answers 200 and `https://<host>/` answers the SPA with the `content-security-policy` header.

## Environment

| Variable | Source | Purpose |
|---|---|---|
| `DATABASE_URL` | Supabase session pooler, `alicerce_app` | Requests, jobs and cache |
| `MIGRATION_DATABASE_URL` | Supabase session pooler, `alicerce_owner` | Migrations at boot |
| `SECRET_KEY_BASE` | generated by Render | Signed and encrypted cookies |
| `APP_HOST` | optional; defaults to `RENDER_EXTERNAL_HOSTNAME` | Host allow list and links in emails |
| `WEB_CONCURRENCY`, `RAILS_MAX_THREADS`, `SOLID_QUEUE_IN_PUMA`, `JOB_THREADS` | `render.yaml` | One Puma process with jobs as threads, under 512 MB |
| `THRUSTER_HTTP_PORT`, `THRUSTER_CACHE_SIZE` | `Dockerfile` | Port 10000 and an 8 MB response cache |

The session pooler is required: row level security reads a per-connection setting, which transaction pooling (port 6543) would not keep.

## Rotating secrets

- Database passwords: `alter role ... password` in Supabase, update the matching variable on Render, which redeploys. Requests fail from the password change until the new deploy is live, about two minutes on the free instance; rotate the app role in a quiet hour.
- `SECRET_KEY_BASE`: generate a new value with `bin/rails secret`, set it on Render. Every session and signed token becomes invalid, so every user signs in again. Rotate it after any suspected leak.
- Any key found in a commit: rotate it first, then remove it from history; a pushed secret is public even after the commit is gone.

## Rollback

Render keeps previous deploys: Deploys, choose the last good one, Rollback. The previous image keeps working with the newer schema because strong_migrations rejects migrations that would break it (column removals, renames, blocking index builds) unless they are split across releases.
